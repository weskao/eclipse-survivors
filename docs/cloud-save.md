# Google account and Twilight Embers cloud save

The reference is Skyline Rush's Firebase Authentication + Firestore flow. This game uses a **separate Firebase project**, and only Twilight Embers is stored in `twilightEmbers/{uid}` as `{ embers, revision }`. Revision is technical concurrency metadata. No Google name/email, tokens, hero data, research, achievements, run history, settings or other fields are uploaded to Firestore. Google Auth itself provides the identity displayed in the account dialog.

- Guests retain the existing local save. Signing in selects a distinct UID-scoped local progression save; signing out restores the guest save. Non-currency progression is local to that account on that device. Existing guest balances are intentionally not uploaded or merged.
- On login, menu/result transitions, committed balance changes and network reconnection, the client reconciles the v3 wallet. It uses a Firestore transaction and the last confirmed revision stored atomically with the local wallet. Spending and reset can lower the balance; do not use max(local, cloud). Conflicting concurrent changes stay local until the player retries or explicitly restores the cloud balance. Equal resulting balances converge without a second write (independent equal-value operations are not aggregated). Offline writes remain pending in local storage; sign out retains the UID-specific pending save. Injected legacy stores never connect. Unlocked desktop playtests connect only to their separate demo emulator. Unlocked phone playtests can authenticate but never sync synthetic currency to live Firestore.
- The existing v3 local store is a single-writer design. Simultaneous same-account tabs sharing localStorage are not a supported multi-writer workflow. Firestore rules enforce ownership, field schema and revision increments, not server-authoritative gameplay earnings. This is a personal cross-device save, not an anti-cheat economy.

## Setup (project owner, before release)

1. Create or select a dedicated Eclipse Survivors Firebase project, register a web app, enable Google provider in Authentication, create Firestore, and authorize the actual website domain plus approved local development domains. Do not reuse Skyline Rush project or rules.
2. Copy the public Firebase web app config into `VITE_ES2_FIREBASE_CONFIG` as JSON in local `.env.local` (see `.env.example`). Configure the same repository Actions **variable** for the GitHub Pages release build. Do not commit credentials or OAuth secrets.
3. Deploy the rules explicitly using `pnpm dlx firebase-tools deploy --only firestore:rules --project <eclipse-survivors-project-id>`. The repository change does not deploy Firebase. Test against a disposable project before production.
4. Run `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm typecheck`, `pnpm build`. Test Chrome and iPhone Safari Google sign-in/cancel, guest isolation, two distinct accounts, gain/spend/reset, reload and second-device restore, offline recovery, conflicting balances and permission-denied writes. Verify an unauthenticated or different UID cannot read/write the document, and extra fields and invalid values are refused. Check the actual mobile and desktop account dialog layout in both languages.

With no Firebase configuration, the account dialog explains that cloud save is unavailable and guest play remains functional. Real OAuth and Firestore permissions require owner setup and have not been verified by this source change.

## Direct Google sign-in and expedition results

The unsigned-in home and expedition result buttons invoke Firebase Google OAuth directly, with no intermediary game dialog. They reuse the exact Skyline Rush WebP (`src/assets/ui/google-sign-in.webp`, source Git blob `02c51f38140fb8ae66b30a3b93777ef75c5f2ad1`). An authenticated home button remains an account-management entry for sync and logout. The result line displays a successful save only when the current account's acknowledged wallet matches the local v3 balance; it never claims other game statistics are saved. Guest rewards remain in the guest wallet even if the player signs in from results; the Google account has its own wallet. The result prompt makes that distinction explicit. No live OAuth test is implied by emulator results.

### Automated OAuth and wallet integration check

The branch workflow `ES2 Google OAuth and Twilight Embers emulator QA` exercises the actual Vue entry points and Firebase SDK popup with emulator accounts, not real Google credentials. It checks a desktop login, an actual engine settlement and spending, second-device wallet restoration, and a guest login from a short landscape result without a nested custom dialog. The DEV fixture is outside the production entrypoint and refuses non-loopback or non-emulator execution. Production verification still requires the dedicated Firebase project, deployed rules, authorized domain and a real account.

## Skyline Rush development parity

- `make dev` starts Auth/Firestore Emulator on loopback (9199/8180) and opens Vite at 127.0.0.1. No production Firebase config or Google credentials required; the popup uses mock accounts. Java 21+ is required. Stop the previous Eclipse Survivors emulator with Ctrl+C before switching modes. These ports are intentionally distinct from Skyline Rush's 9099/8080.
- `make dev-unlocked` / `make test-unlocked` use the separate `demo-eclipse-survivors-unlocked` project, seed test accounts with 100,000 Embers and never modify live saves. The unlocked local progression remains per-page memory. The normal emulator uses `demo-eclipse-survivors` and an isolated browser storage namespace. Both emulator environments are disposable and use no import/export persistence.
- `make phone` / `make phone-unlocked` retain the same phone-dev skill and no-emulator behavior as Skyline Rush. Normal phone login needs a configured real Firebase project and authorized host; unlocked phone login is identity-only and keeps fake currency in memory. No live Firestore writes or false cloud-success messages are allowed in unlocked phone mode. This is necessary because ES2 actually seeds fake currency, unlike Skyline Rush's in-memory cosmetic selections. Never fall back to live Firebase if an emulator was requested from a non-loopback host.
