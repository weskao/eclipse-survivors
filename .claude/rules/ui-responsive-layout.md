# Responsive ES2 gameplay UI contract

- Check desktop, mobile portrait, mobile landscape, tablets, short screens, safe areas, English/Traditional Chinese and browser zoom.
- Prioritize combat: HP, real boss health, timer and input controls stay visible. Do not permanently obscure the center battlefield with secondary objectives or status details.
- Mobile portrait <=700px: use the single existing CombatHud information drawer; start collapsed and allow explicit expand, close, outside-pointer dismissal, Escape, resize/orientation dismissal.
- On touch tablets up to 1100 CSS px, reuse the same information drawer so the permanent equipment bar never competes with joystick, dash or hero special actions. Pointer-capable desktops retain their full HUD.
- Do not clone UI projections, notices, timers or simulation systems. Reuse authoritative HUD content and modal components.
- Respect the configured joystick side and touch scale. Touch targets should reach at least 44 CSS px; the special action stays clear of dash/joystick.
- Use existing ES2 accessible dialogs and custom dropdowns rather than browser-native picker popups. Modal layering must exceed combat HUD and protect keyboard focus.
- Use flex/grid, safe-area insets and 100dvh. Keep panels internally scrollable, translated strings wrap and art remains fully visible.
- Honor interfaceScale, reduced-motion and reduced-flashing settings. Avoid extra per-frame UI computations.
- Avoid touching character identity, character assets or combat engine for HUD-only layout changes.
- Add regression tests before production code, confirm RED, then GREEN and review. Verify portrait expanded/collapsed, boss/wave, simultaneous notices, touch controls both joystick sides, home/pause and real viewport bounds.
- Generated UI mockups are conceptual, not browser evidence. Do not claim runtime visual QA, video or full CI success without actual outputs. Never weaken production-art acceptance tests.

## Universal UI and player-focused visual design

These requirements are mandatory for **every** new/edited player-facing feature (home, selection, heroes, skills, modes, HUD, controls, dialogs, shops, collections, rewards, menus, notices, overlays, future features), not just HUD changes, and **even when the user does not explicitly request RWD**. A viewport-safe screen with unreadably small art/text is not acceptable.

- **Devices:** Review desktop (compact and large), mobile portrait, short mobile landscape, tablet in both orientations, and foldable phones both folded and unfolded. Test intermediate viewport sizes, safe areas, notches, home indicator, keyboard overlays, browser zoom, keyboard and touch input, bilingual text and potential foldable **hinge** or segmented-screen occlusion.
- **Human visual perspective:** Review real screenshots at normal viewing scale as a player would. Use mature game UX principles and familiar patterns of established games of the same genre: recognizable and adequately large character/item artwork, a clear visual focal point, sensible hierarchy, contrast, typography, meaningful selection feedback and consistent button affordances. Design for handheld viewing distance, thumbs, touch and keyboard. Never prioritize decorative density over comprehension; avoid a sterile "everything technically fits" layout.
- **Use unused space:** When vertical or horizontal space is available, expand the important hero portraits, selectable art and primary information naturally; prefer flexible grid/flex remaining-space allocation with bounded min/max to tiny fixed thumbnail heights and large blank areas. Preserve aspect ratio (normally `object-fit: contain`), full-art visibility and original asset identity; do not stretch, crop, distort, shrink text excessively, hide core content or make buttons tiny to compensate.
- **No occlusion:** Primary UI content, buttons, dialogs, selections and essential gameplay must not overlap, obstruct each other, clip or extend beneath a safe-area inset, onscreen keyboard, browser chrome, toast, overlay, touch surface/control hit zone, popover or device fold. Keep all primary interactions visible without scroll when realistically possible. For long content, an obvious internal scroll with accessible title/actions is better than unreadably small text or targets.
- **Primary start action (UX audit, 2026-11-24):** `.es2-start` (「踏入幽暮之門」) must be visible without scrolling at **every** supported viewport, including tablets, unfolded foldables and desktops ≥ 720 px wide. The audit found it 1585–3405 px below the top at 720×850, 768×1024, 1024×768 and 1440×900.
- **Minimum text size (UX audit, 2026-11-24):** player-facing text on mobile, including the HUD, is at least about **11 CSS px**. The audit measured hero stats at 9.4 px, hero numbers at 7.7 px, mode times at 9.3 px and HUD labels at 8 px.
- **Responsive implementation:** Base rules on available width **and height**, including orientation and foldable changes. Reuse shared HTML classes, component architecture and style tokens; never maintain parallel copies of the same game behavior merely to support a device. Touch controls need at least 44 × 44 CSS px hit targets; preserve focus/keyboard behavior, ARIA labels, reduced motion, interfaceScale, high-contrast states and bilingual wrapping.
- **Real browser evidence:** Verify representative viewport sizes such as 320×640, 375×812, 640×320, 812×375, 360×800 (folded), 720×850 (unfolded), 768×1024, 1024×768 and 1440×900, with hinge/window segments if supported. Add screenshots and assert start/primary action visibility, art scaling when space exists, no horizontal overflow, no text/image clipping, no unwanted element intersections and bilingual usability; visually inspect screenshots before claiming QA success.

- **Hero-first lobby:** All six heroes are visible on the initial selection page without category filtering; the nine expedition modes use a separate in-menu page. Keep the five Adventurer Hall entries directly accessible above the selection board on every device. The fixed action dock keeps the selected hero/mode and Start visible, including while scrolling; changing pages must not change the selected hero/mode or start a run. On very short displays allow vertical scroll instead of clipping or shrinking interactive targets below 44px.

- **Expedition brief and visual hierarchy:** Keep the current localized mode name, concise objective summary, selected hero and duration visible in the fixed lobby dock on both pages. The expedition brief is itself the change-mode action; the portal Start remains the strongest visual action, with a full 44px+ semantic button hit area. Prefer theme-specific asymmetry, restrained ornament and distinct silhouettes over uniform boxed controls. Decorative geometry must not clip text or focus outlines. Use static CSS paint and bounded transform/opacity effects, respect reduced motion/flashing, and avoid an extra Canvas/WebGL context or JS animation loop for decorative menu UI.

- **Non-selectable game UI:** Disable native text selection and WebKit long-press text callouts across all rendered game UI (including labels, close icons, buttons, HUD, and body-teleported dialogs). Keep real text-entry controls editable/selectable. Use shared CSS rather than canceling pointer, keyboard or context-menu events; preserve focus, scrolling, normal activation and accessible semantics. Include browser regression checks for both the lobby and dialogs.

- **Desktop contextual details:** Fine-pointer hover and keyboard focus expose hero/expedition dossiers using one shared anchored detail surface; no redundant information button on desktop. Touch retains the existing explicit detail action and modal. Hover must not select a hero or mode, start a run, or clip at viewport edges. Keep one content source for hover and modal, dismiss on Escape/leave, and preserve focus and real click actions.
